# Контекст проекта: карта электричек МЦД

Дата передачи: 2026-10-07. Язык проекта и общения: русский. Часовой пояс: Europe/Moscow.

## 1. Для следующего Codex

Это передача контекста из обсуждения, а не уже работающий репозиторий. Пользователь хочет небольшой локальный MVP карты электричек. Архитектура согласована, данные для первого участка подготовлены. Приложение, сервер, сборщик расписания и анимация пока НЕ реализованы. Живое API трёх выбранных станций в рамках реализации карты не проверено.

Следующий шаг: собрать локальную статичную карту с пятью станциями и фильтрацией загрузки тайлов, затем подключить расписание и движение. Не начинать проектирование заново и не расширять MVP на весь МЦД.

В конце этого файла встроены текущая подробная архитектура и полные JSON-данные. Даже если пользователь передаст только CONTEXT.MD, из встроенных блоков можно восстановить конфиг станций и railway.geojson без нового запроса Overpass. Локальные пути из старого чата не требуются.

## 2. Идея и первоначальные этапы

На карте Москвы отображаются примерные положения электричек по расписанию. Поезда движутся по железнодорожной геометрии; наведение и клик показывают данные рейса. Это расчётное положение, не GPS-трекинг.

Пользователь предложил:

0. Ответить на открытые вопросы.
0.5. Описать архитектуру.
1. Получить ID и координаты станций, сопоставить железную дорогу и сохранить конфиг.
2. Запросить станционные расписания, сопоставить рейсы по номеру и вывести расчётные позиции.
3. Сделать анимацию.

Статус: 0 и 0.5 завершены; этап 1 завершён на уровне подготовленных данных. Карта с этими данными ещё не собрана.

## 3. Решения пользователя

### Покрытие

- Основной тест: Дмитровская, Гражданская, Красный Балтиец.
- Дополнительно по станции с каждого края: Стрешнево и Марьина Роща.
- Опрос API только для трёх внутренних станций. Для двух крайних API не подключаем; отсутствие API у них не исследуем заново в MVP.
- Показываем все электрички, которые возвращает API, включая пригородные и экспрессы.
- Полный каталог станций МЦД и расширение геометрии будут позже.

### Размещение

- Личный экран, который пользователь может показать друзьям.
- Сейчас работаем локально. Позже пользователь перенесёт на TimeWeb.
- Sites допустим для тестирования и отладки, но не обязателен. Развёртывание сейчас не требуется.
- Предложенный стек: PHP 8.2+, JavaScript ES-модули, стабильная версия Leaflet, JSON и GeoJSON без обязательной базы данных и системы сборки frontend.

### Время и движение

- Пользователь назвал режим движением по плану, но явно выбрал departureTime как текущий якорь. Семантика отличия от scheduleTime при задержках ещё не подтверждена; не переключать поле молча.
- Для departureTime = HH:MM:30 остановка с HH:MM:15 по HH:MM:45. Реализация: departureTime минус 15 секунд для прибытия, плюс 15 секунд для отправления.
- Если в API секунды другие, окно всё равно строится как ±15 секунд относительно полученного времени, без обрезания секунд.
- Между двумя известными станционными точками равномерное движение по длине пути, от окончания стоянки A до начала стоянки B.
- Известные времена имеют приоритет перед резервной скоростью.
- При нехватке времён движение по пути со скоростью 60 км/ч. Достаточно одного пригодного якоря, номера и направления, чтобы показывать поезд в резервном режиме.
- В первоначальном ответе пользователь предложил резервное движение без остановок. В более позднем техническом уточнении указал стоянки по общему правилу. В принятой архитектуре позднее уточнение имеет приоритет: на станциях, внесённых в конфиг, резервный поезд стоит 30 секунд.
- Пропущенные остановки из текстового поля stops не парсим.
- По достижении известной конечной внутри геометрии поезд стоит две минуты с момента прибытия, затем исчезает. Это заменяет обычную стоянку, а не добавляется к ней.
- У удалённой конечной нет геометрии в MVP. Её название показывается в карточке, поезд исчезает, полностью покинув покрытие. Край покрытия не считается фактической конечной.
- При устаревании или ошибках API продолжаем использовать последнее успешное расписание. Не замораживаем поезд автоматически. Время обновления показываем.

### Идентификация и интерфейс

- Пользователь подтвердил: trainNo не меняется между станциями одного рейса. Используем его для сопоставления.
- На следующие сутки номер может повториться, поэтому внутренний ключ дополнительно различает дату/временное окно рейса. Не создавать дубль одного рейса при пересечении полуночи.
- trainNo может быть null по ранее исследованному API. Такие записи показываем в списке с причиной отсутствия маркера; не объединяем их по выдуманному номеру.
- Если для размещения не хватает других обязательных данных, запись остаётся в списке с перечислением причин.
- На станции: наведение с названием, клик с ближайшими электричками «в Москву» / «из Москвы».
- На поезд: наведение и клик; карточка с номером, типом, конечной и исходным текстом остановок.
- Состав изображаем «сосиской» физической длиной 160 метров. Она повторяет изгибы пути, а не имеет фиксированную длину в пикселях.
- Общая траектория допустима для обоих направлений MVP; точные станционные пути и стрелочные маршруты реальных поездов не моделируем.

### Опрос

- Не более одного запроса к API МЦД в секунду, включая повторные попытки.
- Станции опрашиваются последовательно.
- После окончания полного цикла ждём две минуты, затем начинаем следующий.
- Сборщик один; несколько вкладок не должны увеличивать число обращений к источнику.
- Сохраняем ранее полученные времена. Исчезновение отправления из табло не означает отмену и не удаляет историческую точку рейса.
- Горизонт приблизительно в 10 ближайших поездов на направление подходит пользователю.

## 5. API МЦД: минимальный контракт для реализации

Источник: неофициальная документация MCD_Nata_Info_API_unofficial_v0.1.md, исследование от 2026-10-06, прикреплённая пользователем. Это публичный API станционных табло, не подтверждённый официальный контракт. В исходном исследовании проверены разные станции D1–D4.

Base URL: https://mcd.nata-info.ru

### Endpoint'ы

```http
GET /api/stations
GET /api/v2?station=4127&build=84
GET /api/v2?station=4128&build=84
GET /api/v2?station=4129&build=84
```

Для карты список станций уже подготовлен; нет необходимости получать /api/stations в каждом цикле.

| Параметр | Наблюдавшееся поведение |
|---|---|
| station | Обязательный внутренний ID; при отсутствии корректной станции наблюдался HTTP 400 Unknown station |
| direction=1 | Фильтр toMoscow=false, «из Москвы» |
| direction=2 | Фильтр toMoscow=true, «в Москву» |
| Без direction | Возвращались оба направления; для сборщика предпочтителен этот вариант |
| build=84 | Версия штатного клиента на дату исследования; это не гарантированно вечное значение |
| trains=10 | Передаётся штатным клиентом; изменение значения в тестах не меняло размер выдачи, не считать обычным LIMIT |
| skip, index | Точная семантика неизвестна; в исследованных тестах не изменили выдачу, для MVP не нужны |
| sos, pid | Для карты не нужны |

При несовпадении build возвращался needReload=true. Не превращать этот флаг в бесконечную перезагрузку независимого клиента. Без direction в тестах было 20 записей, с direction 10.

### Нужные поля ответа

```typescript
interface Train {
  trainNo: number | null;
  toMoscow: boolean;
  departureTime: string; // ISO datetime с часовым поясом
  scheduleTime: string;
  delaySeconds: number;
  trainLength: string; // наблюдались standard и short; enum не закрыт
  i18n: {
    ru: {
      destination: string;
      trainClass: {
        name: string;
        img?: string;
        abbr?: string;
        style?: string;
      };
      stops: string;
    };
    en?: unknown;
  };
  softBreakDestination?: string;
}

interface StationResponse {
  stationId: number;
  stationName: string;
  stationNameLat?: string;
  diameter: number;
  trains: Train[];
  needReload?: boolean;
  // Есть и другие станционные/экранные служебные поля.
}
```

- Строки времени в исследовании имели формат вроде 2026-10-06T15:12:30.000Z. Хранить абсолютное время, выводить в Europe/Moscow.
- В схемах API не обнаружено отдельного времени прибытия. arrival для модели вычисляем по выбранному правилу пользователя.
- departureTime штатный клиент использует для ближайшего отправления. Его отличие от scheduleTime при реальной задержке отдельно не зафиксировано.
- delaySeconds нельзя дополнительно прибавлять к departureTime без подтверждения семантики; в принятом MVP не прибавляем.
- stops представляет текст, например сообщение о всех остановках или исключениях; показываем без парсинга.
- У trainClass встречались разные классы; не закрывать перечень фиксированным enum.
- Для конечной используем i18n.ru.destination, а не softBreakDestination с мягкими переносами.
- from/to/ggs из станционного списка относятся к оборудованию; не нужны карте, не обращаться к внутренним адресам.
- Нужны обработка сетевых ошибок, неверных данных и изменений схемы. CORS и доступность API из выбранной среды ещё не проверялись реализацией карты; PHP-сборщик исключает зависимость upstream-запросов от браузерного CORS.

## 6. Карта, пути и тайлы

Поставщик подложки: Thunderforest Transport. Бесплатный ключ есть у пользователя, но сам ключ в этом разговоре не передан. При реализации предусмотреть локальную настройку ключа; не выдумывать значение и не требовать ключ для отладки самой геометрии на сером фоне.

PNG не распознаём. Источник траектории движения: отдельный railway.geojson из OSM. Для MVP растровая подложка достаточна. У Thunderforest также есть векторный Transport, но переход на него для текущего MVP не требуется.

### Фильтрация запросов

- Коридор релевантности: 500 м от железной дороги/станций выбранного участка.
- Тайл загружаем, если его географический прямоугольник хотя бы частично пересекает коридор.
- Полностью внешние тайлы заменяем серыми ячейками ДО создания внешнего src/вызова fetch.
- Не проверять только центр тайла: можно потерять железную дорогу у края PNG.
- Частично пересекающийся PNG загружается целиком и может визуально содержать территории дальше 500 м. Строгая визуальная маска не включена в принятый MVP.
- Географические расстояния считать в метрах с учётом широты, а не как сырые метры Web Mercator.
- Ограничить панорамирование и масштаб областью участка. Bounds сами по себе не заменяют фильтр тайлов.

### Кэширование и условия провайдера

В разговоре проверены официальные условия Thunderforest: кэш в браузере/на устройстве разрешён, общий кэширующий прокси и перераздача тайлов запрещены. Массовая предзагрузка на бесплатном плане запрещена. Поэтому принят браузерный кэш реально просмотренных тайлов, без общего серверного кэша и предварительного скачивания Москвы.

На дату проверки бесплатная квота была 150 000 tile requests в месяц. Это наблюдение на дату обсуждения; при необходимости дальнейшей оценки бюджета проверить текущие условия. Анимация маркеров не должна перезагружать подложку. Атрибуция Thunderforest и OpenStreetMap contributors обязательна.

## 7. Как была подготовлена геометрия

Пользователь выполнил запрос в Overpass Turbo и передал export.geojson:

```overpass
[out:json][timeout:60]
[bbox:55.7900,37.4800,55.8300,37.6300];
(
  way["railway"="rail"];
  nwr["railway"~"^(station|halt|stop)$"];
);
out body geom;
```

Экспорт содержал 552 объекта: 464 LineString и 88 Point. Было много нерелевантных объектов: станционные пути, соединения, метро, МЦК и одноимённые станции других видов транспорта. Отбор только по названию станции недостаточен.

Из rail-путей с usage=main без service построен неориентированный граф по совпадающим координатам узлов. Найдена непрерывная линия между проекциями крайних станций. Проверено прохождение рядом со всеми тремя внутренними станциями. Между крайними станциями выбран путь из 23 фрагментов OSM; с продолжениями используется 26 исходных ways.

Результат:

- Один Feature с LineString, направленный от Стрешнево к Марьиной Роще.
- 165 вершин.
- Между проекциями крайних станций: 8959,492 м.
- Полная линия с продолжениями: 9459,515 м.
- Западное продолжение: 249,966 м; восточное: 250,057 м.
- Расстояния между соседними станциями: примерно 2293 м, 2089 м, 1633 м, 2944 м.
- Нет выдуманных прямых перемычек между несвязанными путями; проверена принадлежность каждого сегмента исходному OSM.
- Проверены порядок станций, отсутствие повторяющихся вершин и отклонение от пути менее 10 м для всех станций.
- Расстояния рассчитаны по сферической геодезической формуле со средним радиусом Земли 6371008,8 м. Локальная проекция использована для привязки точек к сегментам.
- Это репрезентативная линия для обоих направлений MVP, а не подтверждение конкретного станционного пути реального поезда.

Исходный экспорт около 592 КБ, итоговая геометрия около 18 КБ. В GeoJSON сохранены cumulativeMeters, исходные OSM ID, длины и атрибуция.

## 9. Приёмка и ближайшая работа

Исходные критерии пользователя:

1. Видно участок Дмитровская, Гражданская, Красный Балтиец с продолжениями до крайних станций.
2. Полностью нерелевантные тайлы вне 500-метрового коридора не запрашиваются, вместо них серые ячейки.
3. На станции можно навести указатель и кликнуть.
4. Поезда отображаются составами примерно 160 м длиной.
5. Составы движутся между станциями согласно известным временам, стоят по выбранному правилу и поддерживают наведение/клик.

Следующий порядок реализации:

1. Восстановить встроенные JSON-файлы в каталог config.
2. Сделать локальную карту с геометрией и пятью станциями; ключ Thunderforest вынести в локальную настройку.
3. Сделать собственный слой тайлов с проверкой коридора до сетевого запроса. Проверить Network, клики и карточки.
4. Реализовать отдельный последовательный PHP-сборщик, нормализованные снимки и сохранение временных точек. HTTP-сервер читает готовое состояние, не запускает опрос источника по запросу каждой вкладки.
5. Реализовать сборку рейсов и чистую функцию положения по абсолютному времени.
6. Проверить модель на фиксированных примерах: стоянка ±15 с, движение между двумя точками, один якорь и 60 км/ч, старая выдача, конечная/край покрытия, полночь, отсутствующий номер.
7. Подключить requestAnimationFrame: каждый кадр получает положение из текущего времени, не накапливает шаги. Проверить восстановление после сворачивания вкладки.
8. Проверить живое API трёх станций с согласованной частотой.

Не считать этапы 2–3 выполненными по наличию статичной схемы или этого файла. Не подменять недостающие данные молчаливыми догадками. Отдельно диагностировать режим расчёта и невозможность размещения записи.

## 13. Подробная архитектура, версия содержимого 0.3

Далее приведено актуальное содержимое MCD_Map_MVP_Architecture_v0.1.md. Заголовки исходного документа сохранены.

# Карта электричек МЦД: архитектура локального MVP

Версия содержимого: 0.3. Дата: 2026-10-07. Имя файла сохранено для преемственности.
Этап проекта: этап 1 завершён на уровне данных. Станционная конфигурация и связная геометрия подготовлены и проверены. Реализация приложения в этот документ не входит.

## 1. Назначение и границы

Личный браузерный экран с расчётными положениями всех электричек, возвращаемых API для выбранных станций. Положение рассчитывается по расписанию, а не по данным GPS.

Станции, опрашиваемые в MVP: Дмитровская, Гражданская, Красный Балтиец. Геометрия карты включает продолжение до Стрешнево и Марьиной Рощи. Предположение пользователя об отсутствии API на двух крайних станциях принимается как ограничение MVP, а не как доказанный факт.

Порядок геометрии с запада на восток: Стрешнево, Красный Балтиец, Гражданская, Дмитровская, Марьина Роща. Координаты и ID ниже предоставлены пользователем. Связность линии и проекции станционных точек на неё проверяются при подготовке геометрии.

В MVP нет полного каталога МЦД, парсинга пропущенных остановок, восстановления всего маршрута до далёкой конечной и привязки к конкретным путям на станции.

## 2. Стек

- PHP 8.2+ для локального HTTP-сервера, адаптера API и отдельного CLI-сборщика. Выбор сохраняет простой путь к будущему размещению на TimeWeb; сам деплой сейчас не проектируется.
- Обычный JavaScript с ES-модулями для нормализации данных, расчёта положения и интерфейса.
- Стабильная версия Leaflet для растровой подложки, станции, подсказок и кликов. Конкретную версию закрепить при реализации; alpha-версии не использовать.
- Thunderforest Transport PNG как подложка. Ключ задаётся локальной конфигурацией, не включается в распространяемые исходники. При прямой загрузке тайлов браузером ключ виден клиенту; серверный прокси для сокрытия ключа не предусматривается.
- Проверенная геометрия OSM в локальном GeoJSON. Получение геоданных является подготовкой конфигурации; Overpass не участвует в регулярной работе карты.
- JSON-файлы для сохранения станционных снимков и истории наблюдений. База данных и система сборки frontend для этого масштаба не обязательны.

Для локального запуска нужны два процесса: HTTP-сервер и CLI-сборщик. Долгий цикл сборщика не выполняется внутри обработчика HTTP-запроса. Карта открывается по localhost, не как file://.

## 3. Компоненты и границы ответственности

| Компонент | Ответственность |
|---|---|
| Station config | ID API трёх станций, координаты пяти станций, порядок и положение вдоль линии |
| Railway geometry | Проверенная линия движения и накопленные расстояния в метрах |
| Collector | Последовательный опрос трёх станций, ограничение частоты, сохранение снимков |
| API adapter | HTTP-запросы, проверка структуры, выделение нужных публичных полей |
| Observation store | Последний успешный снимок по каждой станции и ранее полученные временные точки |
| Trip builder | Объединение записей по номеру рейса и дате, диагностика отсутствующих полей |
| Motion model | Стоянки, движение по известным временам, экстраполяция со скоростью 60 км/ч |
| Corridor tile layer | Проверка допустимости тайла до запроса PNG |
| Map renderer | Станции, поезда длиной 160 м, наведение, клики, анимация |
| Details panel | Карточки станций и поездов, список записей, не размещённых на карте |

HTTP-сервер отдаёт карту, конфиг, геометрию и общий снимок расписания. Чтение этого снимка браузером не вызывает дополнительных запросов к источнику МЦД.

## 4. Конфигурация

### Статическая

Для станции: собственный ID, название, API ID или null, координаты, расстояние вдоль линии в метрах, признак наличия расписания, принадлежность к участку.

Для участка: GeoJSON LineString, накопленные расстояния, границы покрытия, направление соответствия toMoscow для данного участка. Не выводить географическое направление из названия конечной и не считать toMoscow глобальной характеристикой рейса для будущего полного МЦД.

Для приложения: 500 м буфера, 160 м длины поезда, 30 секунд стоянки, 120 секунд стоянки на конечной, 60 км/ч резервной скорости, 1000 мс минимального интервала между началами запросов, 120 секунд ожидания после завершения цикла.

Станционная конфигурация сохранена в MCD_Map_MVP_Stations.json. Координаты указаны пользователем в порядке широта, долгота:

У крайних станций apiStationId=null и pollEnabled=false. У трёх внутренних станций pollEnabled=true. Расстояния alongTrackMeters вычислены по выбранной линии OSM. Исходные location сохранены; trackLocation содержит проекцию на путь, trackOffsetMeters показывает расстояние от исходной точки до этой проекции. Координаты станций в конфиге представлены именованными полями latitude и longitude; при создании GeoJSON порядок координат меняется на [longitude, latitude].

### Подготовленная геометрия

Из пользовательского export.geojson (552 объекта) выделена одна непрерывная линия. Основной участок собран из 23 фрагментов OSM; пути соединяются общими координатами узлов, искусственных перемычек между несвязанными путями нет. В исходный граф включены railway=rail с usage=main без service. После выбора пути остальные пути исключены из итогового GeoJSON.

railway.geojson содержит один Feature с LineString, направленный от Стрешнево к Марьиной Роще. Длина между станционными проекциями: 8959,492 м. По обеим сторонам добавлены продолжения примерно по 250 м по существующим путям OSM. Полная длина: 9459,515 м; вершин: 165. Эти продолжения дают поезду место полностью покинуть основной участок. Начало геометрии расположено до Стрешнево, поэтому её alongTrackMeters не равно нулю.

Это одна репрезентативная линия для обоих направлений MVP. Топология и прохождение через станции проверены; соответствие конкретному пути движения каждого реального поезда не утверждается.

### Динамическая

Снимок станции содержит fetchedAt, lastSuccessfulAt, исходные нужные поля trains[], ошибку последней попытки и текущий статус обновления. История содержит станционные временные точки по рейсам. Сырые внутренние адреса оборудования и конфигурация SOS не сохраняются.

Для каждой записи рейса сохраняются trainNo, toMoscow в контексте станции, departureTime, scheduleTime, delaySeconds, trainLength, destination, trainClass и stops. scheduleTime и delaySeconds доступны для карточки; время движения в MVP берётся из departureTime.

## 5. Опрос API

1. При запуске сборщика читается сохранённое состояние.
2. Последовательно запрашиваются Дмитровская, Гражданская и Красный Балтиец без фильтра направления.
3. Между началами любых запросов к API МЦД выдерживается не менее 1000 мс. Ограничение распространяется также на /api/stations и повторные попытки.
4. После завершения последней попытки цикла сборщик ждёт 120 секунд до следующего цикла. Продолжительность цикла добавляется к этому интервалу.
5. При ошибке сохраняются предыдущие успешные данные станции. Ошибка фиксируется, но не стирает поезда.
6. Новая версия данных публикуется атомарно. Если часть станций обновилась, используется смесь новых и последних успешных снимков с отдельными временами обновления.

Сборщик имеет блокировку от параллельного запуска. Несколько вкладок браузера не умножают опросы источника. Браузер может проверять локальный снимок каждые пять секунд; этот интервал не относится к upstream API.

Размер выдачи принимается таким, каким его возвращает источник. Не полагаться на trains как на рабочий параметр LIMIT. Не строить бесконечные перезагрузки независимого клиента вокруг needReload.

## 6. Сопоставление рейсов

Внутри текущего рейса trainNo принимается устойчивым между станциями, согласно решению пользователя. Дополнительно хранится дата рейса по московскому времени, чтобы одинаковый номер на следующие сутки не перезаписал прошлый поезд.

Дата назначается рейсу целиком по первой известной временной точке, а не независимо каждой станции. Наблюдения после полуночи объединяются с существующим рейсом при согласованной последовательности станций и времён; будущий одноимённый рейс с отдельным временным окном получает другой ключ.

Поезд собирается из всех полученных и сохранённых станционных наблюдений. Исчезновение записи из списка ближайших отправлений не является отменой рейса и не удаляет предыдущую временную точку.

Новые сведения той же станции заменяют предыдущую временную точку для этого рейса. Карточка хранит станционный контекст данных и не предполагает, что текст stops одинаков на всех станциях.

При первом запуске достаточно одной временной точки для расчёта по резервной скорости, если известны номер, время, направление и геометрия. Две и более точки позволяют использовать реальные интервалы расписания.

## 7. Модель времени и движения

Все абсолютные даты читаются с часовым поясом из ISO-строк. Расчёты выполняются по абсолютному времени, отображение по Europe/Moscow. Секунды API не обрезаются.

Для временной точки d = departureTime:

- расчётное прибытие: d − 15 секунд;
- расчётное отправление: d + 15 секунд;
- стоянка: 30 секунд.

Таким образом, для d = 12:34:30 поезд стоит с 12:34:15 до 12:34:45. Если API вернул другое значение секунд, окно всё равно строится относительно этого значения, без округления к :30.

departureTime принимается как выбранный пользователем временной якорь. Режим называется расчётом по времени API: пока не подтверждена семантика полей при задержках, он не гарантирует строго неизменённого планового расписания. delaySeconds дополнительно к departureTime не прибавляется.

### Между двумя известными точками

Для станции A отправление a = dA + 15 секунд, для следующей известной точки B прибытие b = dB − 15 секунд. Между a и b позиция равномерно меняется по расстоянию вдоль железной дороги:

u = (now − a) / (b − a)

s(now) = sA + u × (sB − sA)

Известные временные точки имеют приоритет перед скоростью 60 км/ч. Скорость на таком сегменте выводится из расстояния и длительности. Никаких остановок на непроверенных промежуточных станциях из текста stops в MVP не добавляется.

Если b <= a, сегмент не считается пригодным для движения по расписанию: используется резервный режим с диагностикой «противоречивые временные точки». Деление на ноль и движение назад во времени исключаются.

### При недостатке временных точек

Резервная скорость: 60 км/ч = 16,6667 м/с. Перед первой известной станцией выполняется обратный расчёт от её прибытия; после последней известной станции выполняется прямой расчёт от её отправления.

Если нет пригодного интервала расписания, но есть направление и хотя бы одна временная точка, поезд движется по линии с этой скоростью. Согласно более позднему уточнению пользователя о default-поведении, на станциях, явно внесённых в конфиг, условно стоит 30 секунд. Это уточнение имеет приоритет над ранним вариантом «без остановок до конечной». Неизвестные станции вне конфига не моделируются.

Для согласования с известной временной точкой обратный расчёт включает условные стоянки на известных станциях конфигурации. Нельзя просто умножать время на скорость и затем добавлять остановки, сдвигая заданный якорь.

### Конечная и край карты

Если конечная сопоставлена со станцией внутри геометрии, поезд останавливается там на 120 секунд с момента расчётного прибытия, затем исчезает. Обычная стоянка 30 секунд к этим двум минутам не добавляется.

Если конечная находится за пределами геометрии или не сопоставлена, она показывается текстом в карточке. Поезд продолжает движение до края покрытия, затем исчезает с карты, когда весь состав покинул покрытие. Это не означает достижения настоящей конечной.

Для удалённых конечных геометрию маршрута и координаты в этом MVP не собираем. Последняя станция с данными API сама по себе конечной не считается.

## 8. Устаревшие данные

Последние успешные наблюдения продолжают использоваться независимо от возраста. Автоматическая остановка анимации из-за устаревания не вводится.

Интерфейс показывает время обновления и состояние источника. В карте это обычный информационный статус, а не блокирующее предупреждение.

Использование старых данных не отменяет жизненный цикл поезда: он уезжает за пределы покрытия либо исчезает через две минуты на известной конечной. При недоступном API новые неизвестные рейсы не создаются. При возобновлении API модель пересчитывается по новым данным; возможная корректировка положения допустима для MVP, плавное сглаживание не должно нарушать времена станций.

## 9. Геометрия и отображение состава

Станционная координата проецируется на проверенную линию и получает s, расстояние от её начала в метрах. На станции положение центра поезда совпадает с этой точкой.

Поезд изображается короткой линией с округлёнными концами. Её концы находятся на s − 80 м и s + 80 м. Она повторяет изгиб железной дороги; длина 160 м вычисляется в метрах вдоль пути, не в постоянных пикселях и не в градусах.

Для масштабирования расстояний учитывать географические метры, а не необработанные метры Web Mercator, искажённые широтой. В MVP допускается одна линия для встречных поездов. Их визуальная ширина и удобная зона клика задаются в пикселях, физическая длина остаётся 160 м.

Анимация использует requestAnimationFrame. Каждый кадр получает положение непосредственно из времени, а не прибавляет маленький шаг к прошлой позиции. После сворачивания вкладки и её восстановления поезд сразу занимает рассчитанное текущее положение.

Наведение показывает короткую подсказку. Клик закрепляет карточку. Для пересекающихся составов допустим список выбора рейса в точке клика.

## 10. Ограничение загрузки тайлов

Коридор карты строится вокруг проверенной линии участка и пяти станций с буфером 500 м. Расстояние буфера измеряется в географических метрах.

Тайл разрешён к загрузке, если его географический прямоугольник хотя бы частично пересекает коридор. Проверка по центру тайла недостаточна: такой тест может скрыть железную дорогу у края PNG.

Проверка выполняется в собственном слое GridLayer/createTile до создания изображения с внешним src. Для полностью внешнего тайла возвращается серая ячейка того же размера без запроса Thunderforest. Допустимый тайл загружается только если он требуется текущему виду карты; никакого прогрева всей территории нет.

У частично пересекающегося тайла PNG неизбежно содержит пиксели за пределами 500 м. Для MVP он разрешён целиком. Если позже потребуется строгое визуальное обрезание по коридору, добавляется маска; сама маска не сокращает размер скачанного PNG.

Ограничить панорамирование и диапазон масштабов областью тестового участка. Конкретные пределы zoom выбрать после просмотра карты, чтобы составы оставались различимы. Ограничение bounds дополняет фильтр, но не заменяет его.

Тайлы загружаются напрямую в браузер. Используется браузерный HTTP-кэш для реально просмотренных тайлов. Общий серверный кэш, массовое предварительное скачивание и перераздача тайлов исключены по условиям Thunderforest. Сохраняется атрибуция Thunderforest и OpenStreetMap contributors с рабочими ссылками.

## 11. Карточки и диагностика

| Объект | Наведение | Клик |
|---|---|---|
| Станция с API | Название, время обновления | Следующие поезда «в Москву» и «из Москвы», время, номер, тип, конечная |
| Станция без API | Название, отсутствие расписания | Название и сообщение «Данные расписания для MVP не подключены» |
| Поезд | Номер, конечная | Тип, конечная, исходный текст stops, известные временные точки и режим расчёта |

Текст stops показывается как получен от API. Он не используется для извлечения списка пропущенных станций. Если поле отсутствует, карточка сообщает «неизвестно», а не считает поезд следующим со всеми остановками.

Записи, которые нельзя разместить, остаются в отдельном списке и в карточках станций. Причины: отсутствует номер; отсутствует или неверно время; не определено направление; станция не привязана к геометрии. Одного временного якоря достаточно для fallback, поэтому отсутствие второго якоря не является причиной скрытия.

Отсутствие текстового типа или конечной не блокирует движение при наличии остальных данных; карточка показывает недостающее поле. Отсутствие номера не заменяется выдуманным совпадением по конечной. Такие строки можно различать локальным ключом в интерфейсе, но нельзя объединять между станциями как установленный рейс.

## 14. Приёмка и проверки

- На карте видны Дмитровская, Гражданская и Красный Балтиец; продолжение включает Стрешнево и Марьину Рощу.
- Внешние тайлы за пределами пересечения с 500-метровым коридором не создают запросов к Thunderforest.
- Все пять станций доступны для наведения и клика. На трёх подключённых станциях видны оба направления расписания.
- Все пригодные для расчёта рейсы API отображаются составами длиной 160 м. Непригодные записи доступны с причиной.
- Для якоря 12:34:30 поезд стоит с 12:34:15 до 12:34:45.
- Между известными якорями поезд следует по геометрии и достигает станции в расчётное время.
- При одном якоре поезд использует 60 км/ч и условные остановки по конфигу.
- При достижении известной конечной поезд стоит 120 секунд и исчезает; удалённая конечная не превращает край карты в конечную.
- Исчезновение записи из ближайших отправлений не удаляет сохранённый якорь.
- Ошибка API оставляет последнее успешное расписание в работе, включая анимацию.
- Ни один новый запрос API МЦД не начинается раньше чем через 1000 мс после предыдущего; новый цикл начинается через 120 секунд после завершения предыдущего.
- Несколько вкладок не запускают дополнительных upstream-циклов.
- Переключение вкладки не вызывает накопления ошибки положения; полночь не создаёт дубль одного проходящего рейса.

Проверки модели времени и расстояний выполнить на фиксированных входных данных; проверку тайлов и кликов выполнить в браузере. Не оценивать точность по GPS, которого у MVP нет.
